# 逐页交付与 Rust 规则兼容修复

验证环境：用户运行中的 MoviePilot v3.1.4。正常耗时样本为极速搜索 3.6.4；最新修正版本 3.6.6。

## 已修复的行为

1. 网页搜索一页请求完成后立即交给 MP 原生过滤、匹配、排序；不等待同一关键词剩余页面。各站继续独立抓取，保留末页、错误页事实与默认十页预算。
2. 多页使用来源及页码标识解析任务；累积所有原始候选，最终按来源和页序交给原生排序、目标优先排序、去重。先完成的第二页不能覆盖第一页面。
3. 关闭边抓边洗、客户端续页或音乐分流时保留原生消费者所需的聚合形状，避免原生按来源覆盖数据造成漏页。
4. 对传给 Rust 的规则副本补充字符类内字面方括号的转义。只有 Python 完整正则解析树一致才接受转换；设置、规则选择、级别顺序、大小与下载策略均不改。Rust 仍失败时沿用原生兜底。
5. 兼容转换限于搜索作用域，包括 ID 搜索、标题搜索与新订阅；音乐不转换。演唱会等 Movie/TV 类型按影视处理。

## 根因隔离

当前全部内置与自定义规则逐个通过容器内 Rust 自检。唯一失败的原始规则为 `PreferenceGroup`：

```
ValueError: Parsing error at position 237: Invalid character class
```

该规则把两个反斜线后未转义的左方括号放进字符类。Python 将其作为字面字符，Rust 解释为嵌套字符类。转换前后 Python 解析树一致；2,565 条固定资源样本经 MP 原生 Python 筛选与 Rust 筛选得到相同保留下标和优先级。

此前对白名单 WhiteList 的怀疑已排除，不能继续把它写成责任规则。

## 不带核对开销的实际搜索

《兰香如故》TMDB 282326，全站全页搜索：

| 指标 | 结果 |
|---|---:|
| 首批原生过滤匹配结果 | 7.50 秒 |
| 全部搜索完成 | 131.47 秒 |
| 候选 | 2,107 |
| 最终结果 | 785 |
| 原生 Rust 筛选批次 | 38 |
| Rust 筛选返回 None / 异常 | 0 / 0 |
| 外部 Rust 解析调用 | 713 |
| 解析缓存命中 / 新算 | 848 / 713 |

筛选累计工作线程墙钟 169.017 秒、当前线程 CPU 63.205 秒；显式 Rust 解析累计墙钟 74.133 秒、当前线程 CPU 23.064 秒。这些工作并发重叠，不能相加作为用户等待时间，也不包含 Rust 可能创建的其他线程 CPU。

红豆饭两个关键词均取得至第 6 页后遇到请求/页面解析失败，最后一次请求 15.30 秒。总完成仍受慢站和全部分页的要求限制。此数据不能证明总耗时相对旧版提高：旧版候选数量、站点返回与错误不相同。

站点统计的 mean/wait 原有实现是进程累计值；本次 requests 是差值。不能用累计均值乘本次请求数推导精确的单次站点总耗时。

## 检查方式

98 项离线测试通过，包括逐页提前处理、多页任务并发乱序、全候选保留、原生稳定合并、取消收口、错误传播、规则副本隔离、音乐分流和新订阅作用域。

3.6.5 实际整批核对发现资源集合一致、排列仍不同，不能据此宣称完全等价。根因进一步确认：`SearchChain._remove_duplicate` 是类定义时保存的独立静态别名，替换 `SearchResultOwner` 的同名方法不会影响它。3.6.6 同时覆盖两个入口，并用内核源码中的真实别名增加安装、排序等价及卸载恢复测试。实际运行核对结果待记录。

`/selftest?verify=true` 为诊断模式：逐批同一候选与原生 Python 筛选对照，比较保留下标及优先级，再与原生整批处理比较完整 Context 顺序和内容。核对开销不能作为正常搜索耗时。

自检结果保存于插件数据，`/diagnostics` 可取回最新结果和当前阶段，即使原 HTTP 请求超过客户端等待时间也不必重跑。诊断线程信息只包含函数、文件名和行号，不包含局部变量或凭据。

原始证据保存在工作区 `rust-rulecheck-v363.json`、`lanxiang-performance-v364.json`；完整搜索核对结果另存。
