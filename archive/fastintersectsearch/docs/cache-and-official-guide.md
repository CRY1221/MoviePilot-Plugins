# 3.6.0 搜索计算缓存与官方指南核对

阅读了官方 V3 主指南及其统一缓存专题（2026-10-12，文档仓提交 53fe1dbcb730941e62051e81f3c08f765375f1fb）。

## 本次实现

- 每次影视搜索一个缓存域，跨来源批次和解析线程共享；不同搜索不共享。相同输入并发只计算一次，不同输入仍并发。
- 解析键包含标题、描述、媒体类型、自定义识别词、MP 解析选项指纹和加速器身份。原生解析输出深复制保存及返回，资源间可变字段不共享。
- 消歧调用仍为 MP 的 recognize_by_meta。批次内沿用原生名称/年份键；跨批次要求解析对象证据及解析配置一致，再复用识别结果。最终同作品判断每条资源仍由原生函数执行。
- 不缓存优先级规则、最终匹配布尔值、下载决定，不提前删任何资源。音乐和未进入加速搜索域的调用走原生逻辑。
- 每类缓存最多 4096 条，达到上限后直接计算。异常不缓存；搜索完成、异常、取消后解除上下文，已有线程按原有收尾流程结束。
- 日志和自检返回解析/消歧命中数、实际计算次数、计算累计耗时，以及过滤和匹配累计工作线程耗时。并行累计耗时可能超过搜索墙钟时间，不能直接相加作为端到端耗时。
- 本次缓存覆盖经过 SearchResultOwner 的影视资源解析；标题搜索独立构造 MetaInfo 的路径、规则引擎内部解析及订阅已有检查点缓存，不宣称都被本次缓存覆盖。

## 官方缓存专题对方案的帮助

主指南推荐 app.sdk.cache；缓存专题仍示范 app.core.cache，与主指南的新代码要求冲突，因此以主指南和当前 SDK 为准。官方缓存提供区域隔离、TTL、内存/Redis/文件后端及清理入口，适合未来经验证的跨搜索复用。

本次不直接套 TTL 装饰器：搜索内复用需要明确生命周期、同输入并发合并和对象隔离；跨搜索持久化还需要识别数据来源、配置更新和失败恢复的失效策略。避免先把重复计算问题扩大为全局缓存问题。

## 指南与现有代码的比对

符合：V3 目录/主类/清单对应、生命周期方法、Vuetify JSON 表单、插件 API 的 apikey 认证、没有直接修改宿主 ORM、没有新增第三方依赖、测试不在运行源码目录、版本和 history 同步。本次将主类及新缓存日志改为 app.sdk.logging。

明确限制：搜索调度和解析适配依赖私有内核函数，不属于完全基于稳定 SDK 的插件。现有接口签名与未知包装器检查可提前拒绝部分不兼容，不能证明相同签名的未来版本语义相同。多个虚拟分身会争用全局搜索方法，不适合启用多个实例。

待后续改善：离线测试使用替身包 fastsearch，而非生产 app.plugins 路径；测试目录尚为 tests/，非指南建议的 tests/v3/fastintersectsearch/。它们没有复制进插件运行目录，但不能将离线测试替代真实宿主加载。处理池停用允许在途任务收尾，也需要真实重载验证资源释放。
