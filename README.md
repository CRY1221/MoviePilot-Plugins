# 极速搜索 · FastIntersectSearch

> **状态：已归档 · 不再维护（2026-10-13）**
>
> 这个插件的初衷是让 MoviePilot 的全站搜索快起来。做下来的结果是：瓶颈不在调度，
> 而在上游解析器的一个缓存容量缺陷 —— 它已被修复，插件也随之失去存在意义。
> 代码与全部版本历史（V2 19 个版本、V3 36 个版本）保留在本仓库，供参考。

## 初衷

MoviePilot 一次全站搜索实测要 **514 秒**（2026-10-13，《兰香如故》TMDB `282326`，9 个站点）。
抓取本身只占一小部分，用户大部分时间花在等待上。

此前做过一版（`plugins.v2/`，冻结在 2.6.0）。它确实快了，但代价是越界：自建过滤、
自己决定保留哪些资源、自己排序。而这些本该由 MoviePilot 说了算 —— 规则、识别词、
优先级、下载决策都是用户在 MP 里配的，插件不该另立一套。

V3 想重做一遍，原则是：**只加速，不越界**。规则选择、过滤、识别、排序、去重和下载决策
全部交回 MP，插件只负责调度与观测。

## 做了什么

- 跨站并发、同站不并发；节奏交给站点自己配的流控
- 逐页交付：每页抓完立刻跑 MP 原生过滤/匹配并推送，不等整轮结束
- 单次搜索内复用解析与消歧结果
- 覆盖网页、通知渠道 / 智能助手、新订阅首次搜索
- 页数上限、中英搜索、订阅按集下载收敛到同一制作组
- 原生调用探针与 `/selftest` 自检接口，用于逐版本对比

## 发现了什么

实测耗时分解：**解析占总耗时 76%–95%，稳定 81 毫秒/次**，过滤只占 1.5%–4%。
站点抓取是网络时间，动不了。

根因不在插件能碰的地方。`MoviePilot-Rust` 的正则编译缓存只有 **256 槽**
（`src/metainfo/custom_words.rs`），而线上有效识别词有 **401 条**。工作集超过容量后
LRU 命中率趋近 0，每条标题要重编译约 145 个正则。

逐档加词的实测拐点与「有效条目数越过 256」完全对齐：

| 取词表前 N 条 | 有效条目 | 每次解析 |
|---:|---:|---:|
| 384 | 244 | 4.3 ms |
| 400 | 260 | ★ 越过 256 |
| 448 | 305 | 69.4 ms |
| 584 | 401 | 82.0 ms |

对照 Python 侧同类缓存，Rust 反而是三者中最小的：Python `re` 内建 512、
`app/domain/meta/words.py` 的 `@lru_cache` 1024、**Rust 256**。

已提交上游：[jxxghp/MoviePilot-Rust#17](https://github.com/jxxghp/MoviePilot-Rust/issues/17)

## 怎么解决的

上游当天修复，`MoviePilot-Rust` **0.3.8** 于 2026-10-12 发布。同口径实测：

| | 每次解析 |
|---|---:|
| Rust 0.3.7 | **79.944 ms** |
| Rust 0.3.8 | **4.657 ms** |
| Python 参考实现 | 5.208 ms |

修好之后做了背靠背对照（同入口、同输入、同页数，相隔 34 秒各跑一次）：

| | 插件开 | 插件停（原生） |
|---|---:|---:|
| 总耗时 | 17.1 秒 | 20.5 秒 |
| 抓取候选 | 653 | 603 |
| 「抓完 → 出结果」 | **5.0 秒** | **4.7 秒** |

**计算段只差 0.31 秒 —— 持平。** 那 3.4 秒的总差全部来自某一次站点响应波动
（插件那次 8 秒拿到 50 条，原生那次 15 秒超时拿到 0 条），不是插件的功劳。

插件原先为绕开该瓶颈写的「词表超限改走 Python 解析」也随之删除（3.6.23）。

## 结果

**根因在上游，上游修了，插件就不必要了 —— 项目就此停止。**

插件唯一独有的是**感知速度**：流式入口在站点结果到达时就给出真结果
（实测第一条真实结果 **3.9 秒**到达），而原生的精确 / ID 搜索要等整轮跑完才给真结果。
这条结构性差异依然成立，但不足以支撑一个常驻插件。

## 代码与配置

代码位于 `plugins.v3/fastintersectsearch/`，清单为 `package.v3.json`。
原 `plugins.v2/` 与 `package.v2.json` 冻结保留。

- 网页：各站点独立推进关键词；保留原生流式事件、来源标识及翻页事实。
- TG / 智能助手：复用原生搜索链、跨站并发与分页。
- 同站保护：同步与异步搜索共用进程内队列，同站只允许一个真实在途请求；默认不额外等待（0 秒）。
- 首订：仅匹配 `source=new` 且执行身份一致的任务，并发预取每站当前一页。
- 排序：标题搜索的最终展示也调用 MP 的 `TorrentHelper.sort_torrents`；不给全集自定义加分，
  不保留已被规则拒绝的资源。
- 音乐：纯音乐透传；被识别为电影或电视剧的演唱会、歌舞剧视频按影视处理。

设置页只保留需要用户决策的控件：

| 配置 | 默认 | 行为 |
| --- | --- | --- |
| `enabled` | 关 | 启用前核验宿主接口，失败则不安装调度适配 |
| `site_sleep_seconds` | **0** | 只保证同站不并发，不在两次请求之间加时间；站点自己配了间隔就按站点的来 |
| `max_pages_per_site` | 1 | 每站每关键词最多翻页数（1–20）；空页或出错自动停止 |
| `bilingual_names` | 开 | 只用原名、中文名、英文名（最多 3 个）替代 MP 的全别名展开 |
| `accelerate_new_subscribe` | 开 | 接管订阅的搜索与下载，并让 `single_group_download` 生效 |

`streaming_pipeline`（边抓边洗）与 `single_group_download`（一季同组）是默认行为、不给开关；
代码仍读配置、缺省为开，老配置里显式关掉过的仍然算数。

## 验证与边界

开发基线：MoviePilot `v3.1.4`（提交 `09f62ff8`），末尾随实例升到 `v3.1.5`。
插件使用私有内核接口，未来相同签名但不同语义的版本仍需重新验证。

离线测试使用固定内核中的原始函数定义和纯领域模块，对外部网络、数据库、识别服务及
下载提交使用替身。未完整启动 MP 容器，不能把离线通过称为线上联调或性能验收。
详情见 [验证记录](docs/refactor-validation.md) 与 [设计说明](docs/refactor-design.md)。

测试环境：Python 3.14、pytest、Pydantic 2。将固定内核 checkout 放在仓库同级
`kernel-reference/`，或通过环境变量 `MP_KERNEL_REFERENCE` 指定路径，再运行
`python -m pytest tests -q`。

限制：站点锁只覆盖本进程经 SearchChain 的影视资源请求，不是跨容器或全系统站点限流器。
首订预取可能产生少量最终未消费的请求，但不会替它们推进游标、写检查点或提交下载。
